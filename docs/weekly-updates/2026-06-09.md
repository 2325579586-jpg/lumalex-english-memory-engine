# Weekly Update: CI and Contribution Intake

Date: 2026-06-09

## Goal

Make LumaLex look and feel more trustworthy to GitHub visitors by adding a visible build check and clearer contribution intake paths.

## Motivation

The project already has a strong product README and a working Vite frontend build, but new contributors had no GitHub-native workflow, PR checklist, or issue templates. That made the project look less ready for outside collaboration than the codebase actually is.

## What Changed

- Added a GitHub Actions workflow that installs root API dependencies, installs frontend dependencies, and runs the real frontend production build.
- Added a pull request template with weekly goal, growth rationale, checks, and rollback sections.
- Added bug report and feature request issue templates that ask for reproducible scope without requesting private data.
- Updated README, TODO, and CHANGELOG so the repository documentation matches the new contributor workflow.

## Impact

- GitHub visitors can see that pull requests have an automated frontend build path.
- Contributors have a clearer path for filing focused bugs and feature ideas.
- Maintainers get more consistent PR descriptions with testing and rollback notes.
- The project gains a stronger weekly maintenance signal without changing product behavior.

## Validation

- `npm.cmd install`
- `npm.cmd run build` was checked and is not defined at the root.
- `cd frontend; npm.cmd install`
- `cd frontend; npm.cmd run build`
- `cd frontend; npm.cmd run lint` was checked and is not defined.
- `cd frontend; npm.cmd test` was checked and is not defined.
- `cd frontend; npm.cmd run typecheck` was checked and is not defined.

## Next Suggestions

- Add a dedicated frontend `typecheck` script so CI can expose the TypeScript phase separately from Vite build.
- Add a small docs page explaining the offline-first sync model and where API payloads are guarded.
- Add homepage Open Graph metadata and a GitHub CTA so shared links and first visits convert better.
